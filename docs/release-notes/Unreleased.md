# PXL Unreleased

A custom `pattern` no longer accepts a value it can only read the front of, copying a cell no longer takes the note and link off the cell it copied from, cloning a sheet no longer leaves half its print area pointing at the sheet it came from — or fails outright on a name the workbook already holds — a `@Valid` sheet field no longer gets its rows validated twice, the `util/` helpers no longer answer a missing argument with a raw POI or JDK exception or lose a cell's formatting without a word — plus the javadoc now says what the code does, in the handful of places where the two had drifted apart.

Pre-1.0 release with **one source-breaking change**, confined to the `util/` helpers: a handful of them now declare a checked `PxlNullPointerException` or `PxlArgumentException` they did not declare before, so a call site that catches `PxlException` compiles unchanged while one that catches something narrower has to widen. Nothing else needs recompiling, and annotation-driven import/export reaches none of those signatures. There are also **behavior changes**: on import, cell values that a numeric or `java.util.Date` pattern matched only partly used to bind silently and now raise `PxlCellCodecException`, and a numeric cell just under an undocumented cutoff no longer reads as `false` for a boolean column; on both directions, a `@PxlSheet` field marked `@Valid` now has its rows validated once rather than twice, and a sheet PXL does not process is no longer validated at all; and in the `util/` helpers, `PxlSheetUtils.cloneSheet` renames the clone rather than failing when the name it is given is taken. See the highlights below and the [CHANGELOG](../../CHANGELOG.md).

## Highlights

  - **A `pattern` must match the value in full.** A patterned column was parsed with `DecimalFormat.parse(String)` / `SimpleDateFormat.parse(String)`, and both stop at the first character the pattern cannot read, then report success with whatever came before it. Under `"#,##0"`, `"123abc"` bound as `123` and `"1e3"` as `1`; under `"yyyy-MM-dd"`, `"2024-01-02 xxx"` bound as 2 January 2024. The damage was quiet by construction: `1` is a perfectly plausible quantity, it satisfies `@Min`, and it exports again as `1`, so nothing downstream could tell that the cell had said something else. Worse, it inverted the point of the attribute — naming a pattern made a column *more* permissive than leaving it off, where `Integer.parseInt` and `LocalDate.parse(CharSequence, DateTimeFormatter)` have always demanded the whole string. Parsing now runs through a `ParsePosition` and refuses anything left over. This reaches every value that arrives as text: an Excel STRING cell, every CSV field, and each element of a `Collection` column.
  - **What does not change.** A value the pattern reads end to end still binds exactly as before, prefixes and suffixes included (`"$1,234"` under `"$#,##0"`, `"50%"` under `"#0%"`, `"1,234"` under `"#,##0"`). Cells that carry a number as a *number* never went through the pattern at all, so numeric cells are untouched, and so is the export direction, which formats rather than parses. Two edges are worth checking against your data: with `importTrim = false`, trailing whitespace (`"123 "`) is itself unconsumed input and is now rejected; and only consumption is verified, so a misplaced grouping separator (`"1,2,3"` → `123`) still parses, because `DecimalFormat` does not check group sizes.
  - **`java.util.Date` was the same defect, and its fallback chain absorbs the fix cleanly.** A `Date` column tries its own pattern, then the built-in read formatters, then an ISO-8601 instant. A pattern that matches only part of the value now counts as a miss rather than a match, so the later parsers get their turn and the value is refused only if none of them takes it whole. The export side parses too — a `Date` column's `exportSample` is a raw string the export formatter reads — and it is held to the same rule.
  - **`BigInteger` and `BigDecimal` no longer meet infinity with a `ClassCastException`.** Their formatter runs with `setParseBigDecimal(true)`, which nonetheless hands back a `Double` for the infinity and NaN tokens (`"∞"`, `"NaN"`), and the codec cast the result to `BigDecimal` without looking. The importer wrapped it with the cell coordinates so nothing escaped, but the message named a failed cast instead of the offending value. Neither token has a `BigDecimal` form; both are now refused with the same diagnostic the `Double` and `Float` codecs already use.
  - **A boolean column read `1e-8` from a numeric cell as `false`.** The conversion compared the cell against an epsilon — `Math.abs(value) > 0.0000001` — rather than against zero, so any magnitude at or below `1e-7` was flattened to `false`. No note anywhere explained where that cutoff came from, and the REFERENCE has always described the rule as "a numeric cell is `true` when it is not 0", so this was the code disagreeing with its own documentation rather than a policy anyone had chosen. The comparison is now `value != 0`. Both signed zeros remain `false`, and the only values that change are the ones the epsilon used to swallow.
  - **An empty CSV value put a space in a `char` column.** `char` cannot hold `null`, so the codec had to invent something for an empty value and picked `' '` — a real character, 0x20, that the field then carried as if the cell had said so. The Excel side never agreed: a blank cell is dropped by the resolver before any codec runs, so the field simply kept what it already held. The same absent value therefore meant two different things depending on where it came from, and `char` was the only primitive where you could see it, since `int` and `double` already answer `0` and `0.0`. An empty value now parses to `(char) 0` on both paths, which is what an unset `char` field holds anyway.
  - **A picture column stopped being a picture column when the value started with `=`.** The String export tested the value for a leading `=` before it consulted a single option, so `exportStringAsPicture` was only reachable for values that did not start with one; a row holding `"=SUM(1,2)"` was written as quote-prefixed text that nobody had asked for. The giveaway was the `Collection` path, which has no such test at all — the same annotation behaved differently depending on whether the field was a `String` or a `List<String>`, and nothing documented the difference. The options now choose the form first, and `exportStringAsFormula` wins over `exportStringAsPicture` when both are set. The quote prefix is unchanged in what it does: it is a safeguard on how a plain-text value is written, so Excel shows a leading `=` verbatim, not a third way of deciding what the cell becomes.
  - **Copying a cell took its note and link away from the cell it copied from.** `PxlCellUtils.copyCell` read the source cell's `Comment` and `Hyperlink` and handed those very objects to the destination's setters — but POI re-anchors what it is given, so the call was a move, not a copy: the source cell came out empty. The shape that makes this hurt is the one the helper exists for. `PxlRowUtils.copyRow` and `copyRowMultiplyByRange` copy a template row cell by cell, and by the second destination the source had nothing left to give, so a note written once on a template survived on exactly one row — the first on XLSX, the last on XLS, where an `HSSFCell` goes on answering with the comment reference it caches while the sheet anchors only one, so the file you opened afterwards was the first place the loss was visible. Across workbooks it was stranger still: the comment never attached to the destination and relocated to the destination's coordinates *inside the source workbook*, and the hyperlink came out shared by both workbooks, where changing the copy's address changed the original's. Both are now re-created as new objects owned by the destination sheet, carrying text, author, visibility, link type, address and label, and a copied comment keeps its source's anchor size over the destination cell. One trade-off is deliberate: the text is re-created as plain text, so a comment's rich-text runs are flattened. This is a `util/` helper — the import/export core never called it, so nothing changes for annotation-driven work.
  - **Cloning a sheet left half its print area pointing at the sheet it came from.** POI's two print-area calls are not symmetric: `getPrintArea` hands back a reference with the sheet name in front of *every* range, while `setPrintArea` wants the ranges bare and puts the destination sheet's name on each one itself. `PxlSheetUtils.cloneSheet` bridged the two by cutting the string at its first `!` — exactly right for one range, wrong for anything else. A print area of several ranges (`S!$A$1:$B$2,S!$D$1:$E$2`, an ordinary thing to set in Excel) kept `S!` on every range after the first, so the copy carried a reference that still named the original wherever the result was accepted at all. And because `!` is not a character Excel forbids in a sheet name, a sheet called `A!B` has its name quoted rather than rejected, and the cut landed *inside* the quotes and broke the reference. Ranges are now separated on the commas that sit outside a quoted name, and each range loses everything up to the first `!` outside the quotes, so a name holding a comma, a `!`, or an escaped quote (`O'Brien` → `'O''Brien'`) comes through whole. The clone is also given its final name before its print area is set, because `setPrintArea` stamps whatever name the sheet is carrying at that moment. This is a `util/` helper — the import/export core never calls it.
  - **Cloning a sheet under a name the workbook already holds no longer fails.** The requested name was run through `WorkbookUtil.createSafeSheetName` — invalid characters replaced, 31 chars at most — and applied as it stood, and POI's `setSheetName` turns down a name another sheet already holds, in whatever case it is asked in. The failure was raw POI (`IllegalArgumentException`, not a `PxlException`), and it arrived too late to undo anything: the clone had joined the workbook two calls earlier, so what the caller was left holding was an extra sheet carrying POI's interim name and missing its print area. Everywhere else in PXL a sheet name is made unique before it is used — it is how an export names the sheets it writes and how a dropdown sheet is named — so the helper now does the same, appending a `" (2)"`, `" (3)"` … suffix within the 31-char limit. Two details follow. The name is settled *before* the clone joins the workbook, so the interim name POI hands the clone (`"Src (2)"`) is not read as a collision and does not push the requested name one number further along. And the name the clone ends up with is no longer guaranteed to be the one asked for, so read it back with `workbook.getSheetName(workbook.getSheetIndex(clone))` where that matters. A name no other sheet holds is applied unchanged, and this too is a `util/` helper the import/export core never calls.
  - **Copying a cell across workbooks could drop its formatting and say nothing.** A workbook holds a bounded number of cell styles — 64,000 for XLSX, 4,030 for XLS — and past that POI refuses to make another with an `IllegalStateException`. `PxlCellUtils.cloneCellStyle` caught that, threw it away and returned `null`, which `copyCell` reads as "there is no style to set", so the destination cell got the value and none of the formatting while the copy reported success. The reach is narrow, because `copyCell` clones a style only when the two cells belong to different workbooks — within one workbook they share the style object outright — but inside that case it is the quietest kind of loss: the rows past the limit come out plain and the file looks finished. The failure is now an SLF4J `WARN` carrying POI's own message, exactly as the export path already reports a style it cannot create, and the copy still goes through unstyled rather than aborting a long run over one cell. A style that was created before the failure is discarded rather than returned, so a blank style no longer stands in for a copy of the source.
  - **The `util/` helpers answered a missing argument with someone else's exception.** `PxlWorkbookUtils.createFormulaEvaluator(null)` came back as a bare `NullPointerException` from `workbook.getCreationHelper()`, `PxlSheetUtils.cloneSheet(null, …)` the same, `PxlMiscUtils.convertColumnStringToColumnIndex(null)` and `convertCellReferenceStringToIndexes(null)` as an NPE from inside POI, and `PxlCellUtils.addPicturesToCell(…, horizontalImageNum = 0)` as `ArithmeticException: / by zero` — that one sizes the picture grid with `(imageNum + n - 1) / n` before it checks whether there are any images, so it failed even for an empty list. None of these was a `PxlException`, which is the one promise the library makes about what crosses its boundary, and the same package's other entry points have always kept it. Every one of them now runs through `PxlAssertSupport` and raises `PxlNullPointerException` or `PxlArgumentException`.
  - **A column reference that was not column letters returned a number anyway.** `convertColumnStringToColumnIndex` handed its argument straight to POI, and `CellReference.convertColStringToIndex` does not check what it is given: it folds every character into the same running total, so `"1"` came back as `-16` and `"A1"` as a plausible-looking `10`. Nothing threw, and a negative or wrong column index is not something a caller is likely to test for. The shape is now settled before the call — optional `$`, then letters — and anything else raises `PxlArgumentException`.
  - **A `@Valid` sheet field had every row validated twice, and the worse of the two reports won.** In the workbook form PXL validates each row itself, one at a time, and attaches the sheet name — and, on import, the row index — to the violation. Marking the `@PxlSheet` field `@Valid` asked bean validation to walk those same rows again while it validated the workbook object, so a 100,000-row sheet ran 200,000 validations for an answer that was already settled after the first 100,000. Cost was not the whole of it. On export the workbook pass runs *first* and carries no location, so it was the one that reported: a blank name in row 40,000 came back as `'Name' must not be blank.` with nothing to say which sheet, let alone which row, while the pass that knew both sat behind it and never ran. The validator is now built with a traversable resolver that refuses exactly that cascade, which leaves the per-row pass as the single place sheet rows are validated — halving the work and handing the reporting to the pass that can point at the cell.
  - **What follows from having one pass instead of two.** Rows are now validated exactly where they are processed. A sheet the binder skips — `exportEnabled = false` on export, `importEnabled = false` on import — therefore has its rows left unvalidated even if the field carries `@Valid`, because the per-row pass sits behind that same check; validation follows the sheets that are actually written or read, and turning a sheet off through a runtime option lands in the same place as turning it off on the annotation. Nothing else moves: constraints on the collection itself (`@NotEmpty`, `@Size`, …) still apply, the workbook object's own constraints still apply, a `@Valid` on any field that is not a sheet still cascades as it always did, and the sheet form (`sheet(...)` rather than `workbook(...)`) never had a second pass to lose. Both ways of writing the cascade are covered — on the field and as a container element (`List<@Valid Row>`).
  - **Three javadoc statements described behavior the code does not have.** `PxlConstants.DEFAULT_EXPORT_IF_NULL` and `DEFAULT_EXPORT_IF_EMPTY` were documented as deciding whether a *cell* is written for a null or empty value; they decide whether the **sheet** is created when its row collection is null or empty, which is what `@PxlSheet` and the REFERENCE already said. `PxlImportSheetOption.importExcludeHiddenRows` / `importExcludeHiddenColumns` read "whether to import hidden rows/columns" — the opposite of the flag, which **excludes** them. And `PxlColumnSupport` pointed at `@PxlColumn(exportDropdownList)`, an attribute that does not exist; a dropdown comes from `exportOptionItems` or, for an enum column, `exportEnumDropDownListStyle`.
  - **Two `{@link}` references pointed at a type that was not in scope.** `PxlExportWorkbookOption` linked `PxlSheet#exportCsvCharset()` and `PxlSheet#exportCsvDelimiter()` without importing `PxlSheet`, so neither resolved and both rendered as plain text where the CSV cascade is explained — the one place a reader is being sent to the sheet-level counterpart. They sit on private fields, which javadoc does not process at the plugin's default visibility, so the build never flagged them; the same reference on a public member is an `error: reference not found` that fails it. A javadoc-only import fixes both, and a sweep of every `{@link}`, `{@value}` and `@see` across the module found no other unresolved reference.
  - **Smaller corrections in the same pass.** A doubled brace (`{{@link Date}`) that leaked a stray `{` into `PxlCodecConstants`, a `@param`-count note missing from one diagnostic key, `PxlByteSize#charset()` and its validator explaining the charset in a sentence that did not parse, `PxlTemporalAmountSupport` claiming a token run matches exactly N digits where the regex accepts at least N, and `PxlCellUtils` naming a "no-argument overload" that does not exist. All comment text; no signature, default or message changed.
