# PXL 0.9.6

The diagnostic-message language can be set for one thread instead of the whole process, a missing sheet is reported with the names the source actually holds, `exportTrim` and `exportMasking` reach the three column types that had been quietly ignoring them, an unset `char` column no longer exports as a `?`, and a CSV import that would have dropped extra sources now says so.

Pre-1.0 release with **two additions**, one **behavior change** and **two fixes**. The first addition is `Pxl.setThreadMessageLocale(Locale)` / `Pxl.resetThreadMessageLocale()`, a per-thread tier for the language of exception and diagnostic text; `Pxl.setMessageLocale(Locale)` is untouched in both meaning and behavior, so nothing existing needs to change. The second is that the "sheet does not exist" message now names the sheets the source does hold, with `PxlWorkbookUtils.getSheetNamesOfWorkbook(Workbook)` made public for reading them directly. The behavior change is that a `char`, `Character` or `boolean`/`Boolean` column that sets `exportTrim` or `exportMasking` now writes different text than it did before, because those two options were doing nothing at all on exactly these three types. Every other column type was already unaffected by the defect and is unaffected by the fix. One fix stops an unset `char` column from reaching the sheet as a NUL character, which the XLSX writers were replacing with `?` behind everyone's back; the other closes a hole in the CSV import sheet form, which counted the names it was handed but not the streams. See the highlights below and the [CHANGELOG](../../CHANGELOG.md).

## Highlights

  - **A server could not answer each request in that request's language.** The language of exception text and diagnostic logs had exactly one control, `Pxl.setMessageLocale(Locale)`, and it set the language for the whole process. That is the right shape for the case it was built for — pick a language at startup and keep it — but it is the wrong shape for a web application, where the locale is a property of the request and the framework already keeps it per thread (Spring's `LocaleContextHolder`, `HttpServletRequest.getLocale()`). Calling the one available method per request would have each request overwrite the language of every other request being served at that moment, so the obvious-looking integration was not something anyone could safely write. `Pxl.setThreadMessageLocale(Locale)` sets the locale for the calling thread only and takes precedence there, which makes the filter-shaped usage correct: set it as the request begins, clear it in a `finally`.
  - **The process-wide form is unchanged, and the two compose.** Resolution now runs narrowest first — the calling thread's override, then the process-wide override, then the JVM default — so `setMessageLocale` still means exactly what it meant, still takes effect from a single call at startup, and is still what every thread sees. A thread that sets nothing of its own resolves precisely as it did before. Clearing a thread override drops back to the process-wide tier rather than skipping straight to the JVM default, so an application can keep a global default *and* let individual requests differ from it.
  - **The thread tier asks something of the caller, and it is worth knowing what.** A per-thread value stays on the thread that set it: it does not follow work handed to another thread (a thread pool, `CompletableFuture.supplyAsync`, a reactive scheduler), so it has to be set again where that work resumes; and on a pooled thread it must be cleared before the thread goes back to the pool, or the next unrelated task scheduled there inherits it. Neither applies to the process-wide tier, which is why that one is still the right choice for a fixed language. What is *not* at stake is a classloader leak on undeploy — the value is a `Locale`, so the only cost of forgetting to clear it is a stale language.

  - **"sheet 'Employees' does not exist" told you the one thing you already knew.** The name in that message is the name you wrote in the annotation or handed to `sheet(...)`, so the message repeated your own input back and stopped there — leaving the actual question, what the file *does* contain, to be answered by opening it. A typo, a trailing space, a sheet renamed by whoever produced the file, and a CSV whose filename matches no `@PxlSheet` all arrived as the same unhelpful sentence. The message now names the sheets found in the source as well: the workbook's own sheet names on Excel, and on CSV the file or stream names the caller passed, since there the sources are a list rather than something inside a file. Both languages of the bundle carry the new wording.
  - **`PxlWorkbookUtils.getSheetNamesOfWorkbook(Workbook)` is public**, returning the sheet names in workbook order, taken verbatim — neither whitespace-stripped nor case-folded the way sheet matching compares them, so the result is what someone sees when they open the file. It is the util the importer reads those names through, exposed because listing a workbook's sheets is a reasonable thing to want on its own.
  - **Resolving a sheet no longer opens every sheet in a streaming workbook.** The matching loop compares names only, but it reached them with `getSheetAt(int)`, which on a streaming workbook opens each sheet's own part to build a reader for it — so looking up one sheet opened all of them, once per `@PxlSheet`. Reading through `getSheetName(int)` takes the name from the workbook part that was already parsed. The new util reads them the same way, and for a second reason: it runs while a diagnostic message is being assembled, where a `ReadException` from reaching into a sheet would have replaced the very error being reported.

  - **A masking rule did nothing on a `Boolean` column.** Each codec renders its value to text and then hands that text to one shared step — `PxlStringCodec.makeExportString`, which applies `exportTrim` and then the `exportMasking` regex. Every codec passed through it except three: `Boolean`, `Character` and `char` built their string and returned it as it stood. So `@PxlColumn(exportMasking = "[a-z0-9]")` masked a `String` column and left the `Boolean` column beside it reading `true`, with no error, no warning, and nothing in the REFERENCE to say the attribute did not apply there. A column asking to be masked is asking for one reason, which makes the silence the worst part of it: the export looked done. The three now pass through the same step as everything else, so `true` masks to `****` and a character to `*`.
  - **For `char` and `Character` this was a documented limitation, and it is now lifted.** The type table and the `@PxlColumn` reference both stated that `exportTrim` and `exportMasking` were not applied to those columns, so unlike the `Boolean` case this was a promise being kept rather than a defect. Keeping the promise cost more than it was worth: it left one attribute meaning two different things depending on the column's type, and a single-character column is a plausible place to want a mask. Both notes are gone from the REFERENCE and the two options behave there as they do everywhere else.
  - **`exportTrim` on a character column has one edge worth knowing.** Trimming a value that *is* whitespace leaves an empty string, so a `Character` holding `' '` now writes an empty cell where it used to write a space. That only happens when the field itself carries the character; a `String` source that is blank never reaches the codec, because the resolver answers `null` and blank strings with the column's `exportNullString` before any codec runs. `exportNullString` is unchanged in both what it writes and when.
  - **What does not change.** A column that sets neither option writes exactly what it wrote before, which is every column that never opted in. The import direction never had these two options and is untouched, so a file written by an older version reads the same. And the rendering itself is unchanged — `exportTrueString`/`exportFalseString` still decide what a boolean says, and the first character is still what a `char` column takes from a longer string; the fix is only about what happens to that text afterwards.

  - **A `char` column you never filled in exported as `?`, and nothing said so.** A `char` cannot hold `null`, so a field left alone holds `'\0'` — and unlike every other absent value, that one walked straight past the resolver's null gate, which only knew about `null` and blank strings. The codec then wrote a one-character NUL string into the cell. NUL is a character XML 1.0 forbids, so both XLSX writers replace it with `?` as the file is saved (XSSF through xmlbeans, SXSSF through its own copy of the same rule), and POI has no write-side escape that would have stopped it. The result was a `?` in a column the user had simply not filled in, with no exception and no warning, and a round trip that slid from `'\0'` to `?` to the character `'?'`. With `exportTrim` on it went the other way and vanished into an empty string, so the same data had two different endings depending on an unrelated option.
  - **`'\0'` is now read as the absent value it is.** The resolver's gate takes an unset `char` the same way it takes a `null`, so the column writes its `exportNullString` — the empty string by default — and the NUL never reaches a cell in any format. A boxed `Character` is deliberately left alone: `null` already means absent there, and a `'\0'` in a `Character` is a value the caller chose to put in, which PXL has no business rewriting. What this does not do is fix the underlying limitation — a control character *you* put into a `String` or `Character` column is still replaced with `?` when the file is saved, because that substitution happens inside POI, past the last point PXL sees the value.

  - **A CSV import could throw away every stream but the first.** The sheet form reads one CSV, and it enforced that by counting the names it was handed — never the streams. So `importCsv().sheet(Row.class).fromStreams(names, streams)` with one name and three streams parsed the first stream, returned rows for it, and discarded the other two with no exception, no warning, and nothing in the result to show they had been passed. The workbook form, handed the same mismatch, has always refused it outright. Both lists are counted now, so the sheet form raises `PxlArgumentException` (`builder.import.csv.singleSourceOnly`) when either one runs past a single source — the same rejection `fromFiles` already gave for several files. Reaching this took handing several sources to a terminal that documents itself as single-source, so no correct call changes; what changes is that the mistake now surfaces instead of quietly costing rows.
